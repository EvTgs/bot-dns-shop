# План упрощения filter-snapshot для LLM

## Статус реализации на 2026-05-01

- `filters_llm` добавлен в `context_payload` основного pipeline.
- В runtime наружу уходит компактный слой `groups -> filters -> kind/role/input_mode`.
- Старый `filters_map_summary` пока сохранён как технический fallback для совместимости.
- Следующий незавершённый шаг: убрать остаточную зависимость анализа от `coverage/teacher_contract` в пользу чистого `retrieval_evidence + evidence_ledger`.

## Кратко

Цель: сделать рядом с сырыми DNS-снимками новый LLM-слой, в котором остаётся только структура, полезная для понимания категории и выбора фильтров, без мусора, `null`, длинных бесполезных value-списков и служебных деталей.

Ключевая идея:
- сырой `filters_map` остаётся архивом;
- новый `*_filters_llm.json` становится рабочим представлением для LLM;
- значения фильтров в полном виде не тащатся в общий LLM-контекст;
- отдельно сохраняется различие между:
  - настоящим `range` с произвольным вводом;
  - `range_enum` с дискретными ступенями.

## Новая схема

Целевой LLM-формат для категории:

```json
{
  "product_type": "smartphone",
  "category": {
    "query": "смартфон",
    "section_id": "17a8a01d16404e77",
    "section_url": "...",
    "title": "Смартфоны"
  },
  "groups": [
    {
      "name": "Экран",
      "filters": [
        {
          "id": "f[25s]",
          "name": "Тип матрицы (подробно)",
          "kind": "enum",
          "role": "product_spec"
        },
        {
          "id": "f[2ft]",
          "name": "Частота обновления экрана",
          "kind": "range_enum",
          "input_mode": "discrete_values",
          "role": "product_spec",
          "value_examples": ["60 Гц", "90 Гц", "120 Гц", "144 Гц"]
        },
        {
          "id": "fr[8i]",
          "name": "Высота (мм)",
          "kind": "range",
          "input_mode": "free_range",
          "role": "product_spec",
          "numeric_bounds": {
            "min": 95,
            "max": 184.6
          }
        }
      ]
    }
  ]
}
```

Обязательные поля фильтра:
- `id`
- `name`
- `kind`
- `role`

Опциональные поля:
- `input_mode`
- `numeric_bounds`
- `value_examples`
- `value_count`

## Классификация фильтров

### `enum`

Обычный нечисловой список значений.
Примеры:
- бренд
- тип матрицы
- цвет
- No Frost
- расположение морозильной камеры

### `range`

Настоящий произвольный диапазон.
Используется, если DNS принимает `fr[id]=min-max`, даже если UI показывает bucket'ы.
Примеры:
- высота
- ширина
- вес
- цена
- диагональ

Правило:
- bucket'ы в интерфейсе не считаются ограничением;
- они только подсказки DNS;
- источник истины — поддержка произвольного диапазона в URL.

### `range_enum`

Дискретная числовая шкала без свободного ввода.
Примеры:
- 60 / 90 / 120 / 144 / 165 Гц
- 8 / 12 / 16 ГБ
- 128 / 256 / 512 ГБ

Правило:
- использовать для `>= <= ==`
- нельзя подставлять произвольные числа между ступенями

### `boolean`

Есть/нет, да/нет, toggle.
Примеры:
- NFC
- Wi-Fi
- капучинатор
- влажная уборка

### `service`

Не характеристика товара, а служебный фильтр.
Примеры:
- магазины
- наличие
- акции
- сортировка
- рейтинг/обзоры

LLM по умолчанию не должна использовать `service` как hard-filter слой.

### `unknown`

Только временный статус, если тип не удалось привести уверенно.
В нормальном рабочем файле должен встречаться минимально.

## Что убрать из LLM-слоя

Из нового `*_filters_llm.json` убрать:
- `null`
- пустые массивы
- пустые `selected/default`
- `count`
- служебные `url` у отдельных values
- полные длинные списки values
- магазины по точкам продаж в полном виде
- все поля, которые нужны только UI DNS или отладке

Сохранить только:
- структуру категории
- группы
- минимальные описания фильтров
- указание, как с ними работать (`kind`, `input_mode`, `role`)

## Форматы файлов

Для каждой категории держать рядом:

- `*_filters.md`  
  сырой снимок, не менять

- `*_filters_llm.json`  
  новый основной формат для LLM

- `*_filters_llm_index.md`  
  короткий человекочитаемый индекс:
  - сколько фильтров
  - какие группы
  - сколько `range / range_enum / enum / boolean / service`

Исходный compact-файл можно либо оставить как промежуточный артефакт, либо позже заменить новым `llm.json`, но без coexist нескольких рабочих форматов надолго.

## Правила наполнения значений

### Для `enum`

- если значений мало, хранить `value_examples`
- если значений много, хранить только `value_count` и 3–8 примеров

### Для `range`

- хранить `numeric_bounds`
- bucket'ы не хранить как обязательную часть фильтра
- при желании можно хранить `ui_presets_preview`, но это не должно влиять на логику выбора

### Для `range_enum`

- хранить 4–10 representative значений
- этого достаточно, чтобы LLM понимала шкалу

### Для `boolean`

- значения не хранить вообще, если имя фильтра уже самодостаточно
- максимум один короткий пример: `есть`

## Поведение для последующих этапов

Этот LLM-слой не должен быть источником точного выбора значений.

Дальше pipeline делится так:
1. `filters_llm.json` — структура категории
2. `candidate_packets` — точечные кандидаты под конкретный constraint
3. `coverage` — оценка качества покрытия
4. `ledger` — финальный источник истины для final answer

То есть:
- общий snapshot не должен пытаться решить задачу выбора фильтра целиком;
- он должен только упростить понимание категории и типов фильтров.

## Проверка

### На смартфонах

Проверить, что корректно классифицируются:
- бренд -> `enum`
- год релиза -> `range_enum` или `enum` в зависимости от реального DNS filter shape
- тип матрицы -> `enum`
- частота экрана -> `range_enum`
- высота/ширина/вес -> `range`
- NFC -> `boolean`

### На ноутбуках

Проверить:
- цена/вес -> `range`
- ОЗУ -> `range_enum`
- видеокарта -> `enum`
- покрытие экрана -> `enum`

### На холодильниках

Проверить:
- ширина/объём -> `range`
- No Frost -> `enum` или `boolean` по фактическому shape
- энергокласс -> `enum`

### Acceptance criteria

- исходный `.md` остаётся без изменений
- новый `llm.json` заметно меньше
- в новом файле нет `null`
- фильтр можно понять без чтения полного DNS values dump
- `range` и `range_enum` не путаются
- bucket-only трактовка не применяется к фильтрам с `free_range`

## Принятые решения

- Работаем общей схемой для всех категорий, не только для смартфонов.
- Главный рабочий формат для LLM: `*_filters_llm.json`.
- Полные значения фильтров не передаются в общий LLM-контекст.
- `range` определяется по поддержке произвольного диапазона в URL, а не по виду UI.
- `service` фильтры явно отделяются от `product_spec`.
- Следующий этап после этого — не расширение snapshot, а отдельный `candidate_packet`-слой.
