# План упрощения `*_devices` для LLM

## Статус реализации на 2026-05-01

- `shortlist` и `analysis` payload больше не передают URL товаров в LLM-слой.
- Вместо URL передаётся `code`.
- `raw_additional` добавлен как обязательный fallback в `device_llm_payload`.
- Следующий незавершённый шаг: расширить category-specific normalized fields за пределы текущих `verified_facts`, чтобы shortlist меньше зависел от сырого `raw_additional`.

## Кратко

Цель: передавать в LLM только то, что реально нужно для отбора и сравнения товаров, без лишнего сетевого и служебного мусора.

Ключевые правила:
- в LLM не передаётся `url`;
- вместо URL передаётся только `code` / артикул DNS;
- поле `Дополнительно` не удаляется ни при каких условиях;
- `Дополнительно` сохраняется как `raw_additional`;
- LLM не получает весь каталог, а только предварительно суженный shortlist input.

## Новая схема

Для каждой категории рядом с сырым snapshot держать:

- `*_devices.md`  
  сырой снимок, не менять

- `*_devices_llm.json`  
  компактный LLM-слой

- `*_shortlist_input.json`  
  уже суженный набор кандидатов для LLM

## Что убрать из LLM-слоя

Из `devices_llm` убрать:
- `requested_url`
- `resolved_url`
- `url`
- `mode`
- второстепенные служебные поля парсинга
- полные массивы неиспользуемых характеристик

Оставить:
- `name`
- `price`
- `code`
- ключевые нормализованные поля категории
- `raw_additional`

## Почему в LLM должен идти `code`, а не URL

Для выбора лучших товаров LLM не нужно знать ссылку карточки.

Для внутренней работы достаточно:
- `code`
- `name`

Это даёт:
- меньше токенов;
- меньше шума;
- стабильную привязку к товару;
- возможность потом собрать compare-link или карточку уже во внутреннем слое.

Правило:
- URL хранится только в сыром snapshot или техническом слое;
- в LLM payload URL запрещён.

## Почему `raw_additional` обязателен

Поле `Дополнительно` — это последний сырой fallback-источник характеристик, если structured-поля извлечены не полностью.

Оно особенно важно для:
- смартфонов: RAM, SIM, сеть, NFC, батарея, камера;
- ноутбуков: CPU, RAM, SSD, GPU, разрешение, ОС;
- других категорий, где DNS кратко упаковывает ключевые характеристики в одну строку.

Правило:
- `Дополнительно` сохраняется всегда;
- в LLM-слое оно живёт как `raw_additional`;
- structured-поля и `raw_additional` передаются вместе.

## Как сужать каталог до LLM

LLM не должна видеть тысячи товаров.

Нужна трёхступенчатая схема:

1. `raw devices snapshot`  
   Полный каталог как архив.

2. `devices_llm.json`  
   Все товары категории, но уже в компактном виде.

3. `shortlist_input.json`  
   Только кандидаты после кодового prefilter.

## Правило сужения перед LLM

### Stage A — hard prefilter

Кодом отсечь всё, что точно не подходит:
- бренд
- цена
- год
- память
- RAM
- частота
- тип матрицы
- GPU / CPU / вес / диагональ и т.д. по категории

### Stage B — score

На оставшихся считать простой score:
- совпадение hard-полей
- меньше missing
- лучше soft-сигналы
- цена ближе к цели

### Stage C — dedupe

Убрать:
- один и тот же товар в разных цветах;
- дубли одной модели без содержательной разницы.

### Stage D — LLM input

В LLM отдавать:
- не весь каталог;
- а только `15-25` кандидатов;
- затем LLM выбирает `7 лучших`.

## Acceptance criteria

- в `devices_llm` нет `url`
- в `devices_llm` есть `code`
- в `devices_llm` всегда есть `raw_additional`
- `raw_additional` не заменяет structured-поля, а дополняет их
- LLM получает не весь каталог, а только shortlist input
- формат одинаково работает для смартфонов и ноутбуков

## Принятые решения

- URL в LLM payload запрещён
- `code` обязателен
- `Дополнительно` / `raw_additional` обязателен
- structured-поля + `raw_additional` живут вместе
- shortlist формируется кодом, не LLM
