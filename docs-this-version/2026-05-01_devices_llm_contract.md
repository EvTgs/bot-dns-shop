# Контракт упрощения `*_devices` для LLM

## Кратко

Цель: передавать в LLM только то, что реально нужно для отбора и сравнения товаров, без лишнего сетевого и служебного мусора.

Принятые правила:
- в LLM не передаётся `url`;
- вместо URL передаётся только артикул / код товара DNS;
- поле `Дополнительно` не удаляется ни при каких условиях;
- `Дополнительно` считается обязательным сырым источником для fallback-сравнения;
- LLM не получает весь каталог, а только предварительно суженный shortlist input.

## Почему URL не нужен

Для выбора лучших товаров LLM не нужно знать:
- ссылку карточки;
- `requested_url`;
- `resolved_url`;
- режим парсинга.

Для последующего открытия карточки, compare-link или возврата товара пользователю достаточно:
- `code` / артикул DNS;
- `name`.

URL должен оставаться только во внутреннем сыром snapshot или в техническом слое, но не в LLM payload.

## Отдельный compare-link слой

Compare-link не должен рождаться в LLM-слое.

Правило:
- LLM выбирает кандидатов и формирует shortlist;
- внутренний слой собирает `compare_url` из `code`;
- compare-ветка живёт отдельным канвасом, а не частью LLM-подсказки.

## Почему `Дополнительно` нельзя убирать

Поле `Дополнительно` — это последний сырой источник характеристик, если нормализованные поля извлечены не полностью.

Оно особенно важно для:
- смартфонов: RAM, SIM, сеть, NFC, ёмкость аккумулятора, камера;
- ноутбуков: CPU, RAM, SSD, GPU, разрешение, ОС;
- других категорий, где DNS кратко упаковывает ключевые характеристики в одну строку.

Правило:
- `Дополнительно` сохраняется всегда;
- даже если из него уже извлечены structured-поля;
- structured-поля нужны для ранжирования, а `Дополнительно` — для fallback-проверки и ручной валидации.

## Новый формат `devices_llm`

Для каждой категории рядом с сырым snapshot держать:

- `*_devices.md` — сырой снимок, не менять
- `*_devices_llm.json` — компактный LLM-формат
- `*_shortlist_input.json` — вход в LLM после кодового сужения кандидатов

## Что убрать из `devices_llm`

Из LLM-слоя убрать:
- `requested_url`
- `resolved_url`
- `url`
- `mode`
- все служебные поля парсинга
- полные массивы второстепенных характеристик
- любой декоративный мусор, не влияющий на отбор

Оставить:
- `name`
- `price`
- `code`
- нормализованные ключевые поля категории
- `raw_additional`

## Минимальный контракт товара для LLM

Общий вид:

```json
{
  "name": "6.7\" Смартфон Samsung Galaxy A56 256 ГБ черный",
  "price": 32999,
  "code": "5620468",
  "raw_additional": "ядер - 8x(2.9 ГГц), 8 ГБ, 2 SIM, Super AMOLED, 2340x1080, камера 50+12+5 Мп, NFC, 5G, 4G, GPS, 5000 мА*ч"
}
```

`raw_additional` — это нормализованное имя для поля `Дополнительно` внутри LLM payload.

## Как сужать каталог до LLM

LLM не должна видеть тысячи товаров.

Нужна трёхступенчатая схема:

1. `raw devices snapshot`  
   Полный каталог как архив.

2. `devices_llm.json`  
   Все товары категории, но уже в компактном виде.

3. `shortlist_input.json`  
   Только кандидаты после кодового prefilter.

## Правило сужения перед LLM

### Stage A — hard prefilter

Кодом отсечь всё, что точно не подходит:
- бренд
- цена
- год
- память
- RAM
- частота
- тип матрицы
- GPU / CPU / вес / диагональ и т.д. по категории

### Stage B — score

На оставшихся считать простой score:
- совпадение hard-полей
- меньше missing
- лучше soft-сигналы
- цена ближе к цели

### Stage C — dedupe

Убрать:
- один и тот же товар в разных цветах;
- дубли одной модели без содержательной разницы.

### Stage D — LLM input

В LLM отдавать:
- не весь каталог;
- а только `15-25` кандидатов;
- затем LLM выбирает `7 лучших`.

## Правила по `code`

Поле `code` обязательно, потому что:
- по нему можно собрать compare-link;
- по нему можно вернуть карточку во внутреннем слое;
- он компактнее URL;
- он стабильнее для LLM payload.

Если есть конфликт `code` vs URL:
- в LLM payload оставлять только `code`;
- URL хранить только в сыром snapshot или внутреннем техническом слое.

## Acceptance criteria

- в `devices_llm` нет `url`
- в `devices_llm` есть `code`
- в `devices_llm` всегда есть `raw_additional`
- `raw_additional` не заменяет structured-поля, а дополняет их
- LLM получает не весь каталог, а только shortlist input
- формат одинаково работает для смартфонов и ноутбуков

## Принятые решения

- URL в LLM payload запрещён
- `code` обязателен
- `Дополнительно` / `raw_additional` обязателен
- structured-поля + `raw_additional` живут вместе
- shortlist формируется кодом, не LLM
- compare-link собирается отдельно из `code`
